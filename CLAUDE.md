# Vigie (QHSE) — notes projet

Outil QHSE du système EPC2i (avec Keystone, Codex, Cursus). Maquette source : `design/Vigie.dc.html` (+ `design/_ds/nocturne-…/` pour le design system).

## Next.js 16

Cette version de Next.js a des changements incompatibles avec les versions antérieures (API asynchrones `cookies()`, `params`, `searchParams`…). Lire le guide concerné dans `node_modules/next/dist/docs/` avant d'écrire du code.

## Conventions

- Stack : Next.js 16.4 (App Router) + React 19.3 + Drizzle (PostgreSQL en production, PGlite en démonstration et dans l'application Mac), comme Keystone et Codex. Port de dev : 3200.
- Données : `src/db/schema.ts` → `npm run db:generate` produit la migration dans `drizzle/` ; elle est appliquée à l'ouverture de la base (`src/db/index.ts` : PostgreSQL si `DATABASE_URL`, sinon PGlite), puis, en démonstration seulement, `seed.ts` remplit une base vide. Type commun `Db` / `Tx` / `DbOrTx` (`src/db/types.ts`) : n'utiliser que l'API Drizzle commune aux deux moteurs. Tout écran tolère une base sans site ni personne (amorçage : `src/components/Bootstrap.tsx`).
- Serveur PostgreSQL commun EPC2I (décision M-01, réponses du 18/10/2026) : tables, vues `pub_` et journal (`vigie.__drizzle_migrations`) dans le schéma `vigie` (`SERVER_SCHEMA`, `DB_LAYOUT` de `src/db/migrations.ts`), `search_path=vigie` sur le pool ; `schema.ts` garde `pgTable` et les migrations publiées restent intactes : `migrateServer()` y remplace `"public".` par `"vigie".` au moment de les appliquer, sous `pg_advisory_lock(hashtext('vigie.migrations'))`, sans `CREATE SCHEMA` ; chaque `db.transaction()` y prend `pg_advisory_xact_lock(hashtext('vigie.ecritures'))` (écritures sérialisées comme dans PGlite). PGlite reste dans `public` (journal `drizzle.__drizzle_migrations`). SQL écrit à la main (vues `pub_` : `drizzle/0009_partage.sql`) : noms non qualifiés, ou `"public".` ; jamais une donnée de santé dans une vue `pub_` (`test/integration/server-layout.test.ts`) ; `npm run db:check` étape 6 contrôle la disposition du serveur.
- **Migrations : une migration publiée ne se modifie jamais** (SQL, instantané `drizzle/meta/`, date du journal) — le migrator ne rejoue pas une migration déjà appliquée. Tout changement de schéma passe par une nouvelle migration (`npm run db:generate`), enregistrée dans `drizzle/checksums.json` par `npm run db:check -- --enregistrer` une fois définitive ; `npm run db:check` (CI) vérifie empreintes, journal, `drizzle-kit check`, écart schéma/migrations et application à une base vide. Avant un déploiement : `npm run db:test-migrate -- <sauvegarde>` (migrations appliquées à une copie restaurée).
- Exploitation (`docs/EXPLOITATION.md`) : image Docker (sortie `standalone` avec `VIGIE_STANDALONE=1`, `Dockerfile`, `docker-compose.yml`), route de santé `/api/sante`, sauvegardes (`src/db/backup.ts`, `scripts/vigie-db.ts` : `db:backup`, `db:restore`, sauvegarde automatique avant migration ; restauration : empreintes des pièces jointes contrôlées, archive en clair refusée avec une clé sauf `--accepter-clair`, PGlite rechargé sur place : `VIGIE_UPLOAD_DIR` et `VIGIE_BACKUP_DIR` jamais dans `VIGIE_DATA_DIR`), pièces jointes chiffrées au repos (`src/lib/encryption.ts`, `VIGIE_UPLOAD_KEY` ; lire et écrire les fichiers par `src/lib/uploads.ts` seulement). Une base migrée par une version plus récente est refusée à l'ouverture (`NewerDatabaseError`, `src/db/migrations.ts`) ; purge horaire des empreintes d'IP (`src/db/maintenance.ts`).
- Configuration : variables d'environnement lues et validées (zod) uniquement dans `src/lib/env.ts` — sans `server-only`, pour `src/proxy.ts`, `src/instrumentation.ts`, les scripts et les tests ; le code applicatif passe par `config()` / `isDemo()` de `src/lib/config.ts`. Aucun autre module ne lit `process.env`. Une variable invalide arrête le serveur au démarrage (`ConfigError`, une ligne par variable). Toute nouvelle variable : `env.ts` (+ `src/lib/env.test.ts`), `.env.example` et le tableau du § 4 de `docs/EXPLOITATION.md`.
- Mode démonstration (`VIGIE_DEMO=1`, `npm run dev`, `npm run start:demo`, application Mac par `VIGIE_DESKTOP=1`) : sélecteur de rôle (`setRole`, cookie `vigie_role`), `VIGIE_TODAY`, jeu de démonstration, `/apercu-mobile` ; tout le reste du comportement est celui de la production. Toute fonctionnalité de démonstration se conditionne par `isDemo()` ; hors démonstration, jamais de rôle ni de personne par défaut. Les identifiants du jeu de démonstration (`clefevre`…) ne figurent que dans `src/lib/demo.ts` et les seeds ; destinataires des alertes : `loadQhseLeads()` (`src/lib/data/leads.ts`, responsable QHSE du site, direction et animateurs par `people.last_role`). Date du jour : `today()` de `src/lib/today.ts` (serveur).
- Les indicateurs (TF1/TG, retards, échéances, statuts de contrôles et d'habilitations) sont **calculés** dans `src/lib/queries.ts` à partir des données et de la date du jour — ne pas les stocker. TF1/TG : `safetyRates()` sur les 12 derniers mois complets (`lastFullMonths()`), mois sans heures signalés ; TF1/TG, jours sans accident et pyramide ne comptent que les accidents de l'effectif (`workforceAccident()`) ; qui déclare un AT selon la victime (salarié : CPAM ; intérimaire : l'ETT, informée sous 24 h ; personne extérieure : son employeur) : `declarationDuty()` (`src/components/events/shared.ts`) ; délais d'un AT (48 h CPAM hors dimanches et fériés, option Alsace-Moselle du site, ETT, réserves) : `src/components/events/deadlines.ts` ; heure locale de Paris : `src/lib/dates.ts`.
- Chargements par écran dans `src/lib/data/<domaine>.ts`, server actions dans `src/server/<domaine>.ts` (validation `formReader`, droits `requireManager` / `requireApprover`, site `requireInSite`, `revalidatePath('/', 'layout')`). Les données portant un `siteId` sont filtrées avec `currentSiteId()` / `inSite`, dans le périmètre de la personne (ci-dessous) ; `siteFilter('perimeter')` (et `scope` des chargements de `queries.ts`) pour tout le périmètre. Écran en consultation seule (`isReadOnly(role, écran)`, ex. DUERP pour le Salarié, Audits pour l'encadrement) : écritures refusées par `canEdit(role, écran)` côté serveur, charge de la page sans listes de formulaire ni données d'autrui.
- Session (`src/lib/session.ts`) : `getSession()` → `{ role, user, site, siteOptions, allowedSiteIds, bootstrap, demo }`, redirige sans identité valide (connexion, « Configuration incomplète », « Accès non autorisé ») ; `getOptionalSession()` pour le formulaire public et les routes qui répondent 401/404 ; `currentPersonId()` sans accès à la base (appelable dans une transaction). Identité fournie par `src/lib/auth/` (`getAuthState()` : cookie de démonstration ou session Entra). Pages : `guard(screen)`, doublé avant le rendu par `src/proxy.ts` (`ROLE_ROUTES` et `HEALTH_PAGES` de `src/lib/auth/route-access.ts`, à tenir à jour avec toute nouvelle page : `route-access.test.ts` les compare aux appels `guard()`) ; server actions : `requireManager()` / `requireApprover()` (`src/lib/guard.ts`).
- Sites autorisés : `allowedSiteIds` (null = tous les sites : direction, animateur QHSE, démonstration ; sinon site de rattachement + sites accordés par groupe Entra) ; `inPerimeter(allowed, siteId)` en lecture, `activeSiteIds()` pour les listes de choix ; listes de sites des formulaires : `loadFormOptions()` (`writableSites()` : exactement les sites qu'accepte `requireInSite(…, { create: true })`, `allSites` pour « Tous les sites »). Toute écriture sur une donnée portant un `siteId` appelle `requireInSite(siteId)` après le chargement de l'enregistrement, avec `{ create: true }` pour une création ou un changement de site (site actif du périmètre ; « Tous les sites » réservé au périmètre complet). `setSite` et `/fichiers/[id]` refusent un site hors périmètre.
- Traçabilité : jamais de suppression physique d'un enregistrement métier tracé — archivage (`archivedAt` / `archivedById` / `archiveReason`) ou annulation (`cancelledAt` / `cancelledById` / `cancelReason`), avec un motif obligatoire (`formReader(fd).reason()`, `ReasonButton` / `ReasonForm` de `src/components/ReasonDialog.tsx`) ; chaque création, modification, annulation ou archivage est journalisé par `logChange()` (`src/server/changelog.ts`, `diffFields()`), dans la transaction de l'écriture (paquet 3 : carte du site — activités annulées, jamais supprimées, `site_map` pour zones, voies, plan et échelle —, filières archivées, relevés `consumption`, exigences d'habilitation `qualification_requirement` « personne|titre », cycle de vie des documents). Consultations (SEC-11) : journal distinct `access_log` écrit par `logAccess()` (`src/server/access-log.ts`, jamais bloquant, une entrée par personne et élément sur 10 min) pour toute pièce servie par `/fichiers`, la fiche d'un AT ouverte avec ses données de santé et le registre des accidents bénins ; lu par `loadEventAccesses` (rôles `canSeeHealth`).
- Tests (`npm test`, Vitest) : règles pures dans un `*.test.ts` à côté du module ; server actions et chargements dans `test/integration/`, sur une base de démonstration neuve par fichier (`freshDemoDatabase()`, `actAs(rôle, site)`, `changeLog()` de `test/helpers.ts` ; `next/headers`, `next/cache` et `next/navigation` simulés par `test/next-mocks.ts`), en PGlite en mémoire, ou sur PostgreSQL avec `TEST_DATABASE_URL` (base d'administration : une base créée puis supprimée par fichier, `test/setup-postgres.ts`). Toute nouvelle server action y teste droits, site, motif et journal. Cloisonnement du Salarié dans la charge des pages : `test/e2e/` contre le serveur construit (`VIGIE_E2E_URL`). CI : `.github/workflows/ci.yml` (Node de `.nvmrc`).
- Formulaires : `ActionForm` + `Field`/`Input`/`Select`/`Checkbox` (`src/components/form.tsx`) dans un `Dialog`/`DialogButton` ; à la modification, personne sortie ou site archivé encore portés par l'enregistrement conservés comme choix par `withCurrent` (`src/lib/form-options.ts`), jamais proposés pour un nouveau choix ; SIRET et TVA : `src/lib/siret.ts`. Création d'action depuis un écran source avec `NewActionButton` / `ActionFields` (`src/components/ActionFormDialog.tsx` ; champ `link` = élément lié, source imposée par `sourceChoices` / `lockSource`), rendus pour le QHSE seulement (ci-dessous) ; modification d'une action depuis un écran : `editDefaults` / `editOptions` (`src/components/actions/detail/form-helpers.ts`).
- Éléments d'origine des actions (ACT-01) : une action Documents ou Environnement porte son élément dans une colonne (`documentId`, `wasteStreamId`, `wasteEntryId` ; `preventionPlanId`, `permitId` pour les seules actions reprises), comme `eventId` / `reviewId`, posée **à la création seulement** (lien `link` de l'écran ; une version de document rattachée plus tard ne pose jamais `document_id`), journalisée sur l'action et la source, verrouillée ensuite (recyclage repris : `qualificationPersonId` / `qualificationTitleId`, HAB-04, conservés sur l'action close ou abandonnée et quand le titre n'est plus requis) ; les écrans sources lisent ces colonnes (Documents : aussi `document_versions.action_id` ; Environnement, action « BSD manquants » : le rattachement de l'exigence), jamais `originRef` (texte affiché). Reprise des références textuelles d'une base existante : `npm run db:reprise-liens [-- --appliquer]` (`vigie-db reprise-liens` dans l'image, lit `actions.legacy_origin`), d'office en démonstration. **Habilitations et Prévention ne créent aucune action QSE** (recyclages gérés par le RH, actions immédiates des plans de prévention ; réponses du service QHSE du 15/10/2026) : types de lien `qualification`, `preventionplan`, `permit` refusés à la création et au rattachement (`NON_QSE_LINK_KINDS`), actions reprises affichées en consultation seule (numéro seul quand `canReadAction` refuse) ; un plan de prévention se clôt après un écart R. 4512-6 sans action QSE.
- Plan d'actions QSE (paquet 1, spec `docs/specs/actions-qse.md`) :
  - Règles pures : `src/lib/action-keys.ts` (clés, sans import), `src/lib/domain.ts` (`AVANCEMENT` : 10 avancements en groupes, `isOpenAvancement` = À faire → 80 %, `isClosedActionStatus` = Vérifiée | Abandonnée, `ACTION_SOURCES` : **24 sources** avec cible, chemin et précision, `SOURCE_LINK_KINDS`, `NOTIFICATION_KINDS`), `src/lib/action-rules.ts` (client-safe : `isLate`, Kanban, transitions `transitionKind` / `moveTargets`, `missingFields`, dates, droits, `admissibleSources`, `followUpLinkMode`, filtres d'URL), `src/lib/action-view.ts` (types de la fiche et du formulaire). Serveur : `src/server/action-core.ts` (`nextActionNumber`, `writeAvancement`, `insertComment` ; ne lisent jamais la session), `src/server/action-create.ts` (`createActionRecord`), `src/server/notify.ts` (`notify`, titres, `qhseAnimatorIds`), server actions `src/server/plan.ts` (`saveAction`, preuves), `plan-ui.ts` (`moveAction`, `verifyAction`, `reopenAction`, `abandonAction`), `action-comments.ts`, `links.ts` (registre `src/lib/action-links.ts`) ; chargements `src/lib/data/actions.ts`.
  - Droits (ACT-22 décidé) : **création, modification, transitions et liens complémentaires réservés au QHSE** (`canCreateAction(role)` = `isQhse` = `canApprove`, `requireApprover` ; Direction comptée QHSE) ; l'encadrement lit le plan de son périmètre en lecture seule (`canReadPlan` ; conséquence : À faire, tableau de bord, cloche et badges ne lui montrent plus les échéances des actions dont il n'est pas responsable) ; le Salarié ne lit que ses actions. Le responsable consulte, commente et joint des preuves, sans transition. **Ses propres actions s'ouvrent sur tous les sites** (`canReadAction` : `pilotId === user.id` quel que soit le périmètre ; fiche, `/fichiers`, commentaires, preuves : contrôle « sa propre action » à la place de `requireInSite`) ; rien d'autre d'un autre site n'est révélé (sources en référence seule). Écrans communs (audits, revue, veille) : action décrite seulement si `canReadAction`, sinon numéro seul. Autovérification admise sans marque.
  - Liens complémentaires (ACT-02) : `COMPLEMENTARY_LINK_KINDS` (risque, exigence, contrôle, version de document, revue, décision) rattachés / détachés depuis l'écran source (`LinkActionButton`) ou la fiche action (« Rattacher un élément », « Détacher » : `PlanSource.link` et `linkTargets`, QHSE seulement) par `linkAction` / `unlinkAction` ; refus d'un détachement par `detachBlocked` du registre (AUD-12 : une seule revue par action, dossier d'une revue clôturée figé). Un autre module qui modifie une action (site d'un événement, réserves d'un contrôle, programme de prévention…) l'écrit aussi dans l'historique de l'action, dans sa transaction (ACT-03).
  - Statistiques (ACT-29) : onglet `?vue=statistiques&mois=` de `/actions` (lecteurs du plan) ; calcul pur `computeActionStats` (`src/lib/action-stats.ts`) d'après le journal structuré (`status` / `reprise`, `fromKey` / `toKey`), chargé par `loadActionStats` ; jamais stocké.
  - Source et élément (D20) : la source est **imposée par l'élément lié** (`admissibleSources(kind, facts)` : liste, jamais de source libre ; `[]` = l'élément ne donne pas lieu à une action ; sans élément : les 24 sources et référence d'origine obligatoire) ; un seul événement ou élément d'audit par action, posé à la création, jamais rattaché ni détaché ensuite (`EVENT_AUDIT_LOCKED`) ; actions reprises à plusieurs éléments tolérées. Site obligatoire (jamais « Tous les sites »), `requireInSite(…, { create: true })`, celui de l'élément lié.
  - Actions de suite (vérification « non efficace » / « nouveau risque ») : liens selon `followUpLinkMode` (élément de la source repris, liens multi-porteurs rattachés aussi, éléments à action unique déplacés vers la première suite, journalisés sur les deux actions et la source ; événement clos : référence gardée, échéance « Événement clos — action de suite ouverte » au responsable QHSE du site). « Vérifiée » : nature, constat, résultat et date de vérification ne changent que par « Rouvrir » (motif) puis une nouvelle vérification ; Abandonnée = consultation seule (fil ouvert).
  - « À compléter » (`missingFields`) et retards sont **calculés**, jamais stockés ; règles de dates et de longueur appliquées aux **seules valeurs modifiées** (`actionDateErrors(v, today, changed)`, `textTooLong`) ; champs manquants exigés à la modification suivante. Journal structuré de l'avancement : entrée `status` avec `fromKey` / `toKey` (abandon compris).
  - Numérotation « A-n » : `nextActionNumber(tx)` (compteur `action_counters('A')` dans la transaction de création, toujours au-delà du plus grand numéro vu dans `actions` et le journal). Références des autres fiches (EE-, PP-, permis, documents, FD-, cert-, EV-, PRD-08) : `nextEntityReference(tx, entité, préfixe, chiffres)` (`src/server/references.ts`, même table, portée « ref:<préfixe> ») dans la transaction de création, jamais `nextRef` (aperçu côté navigateur seulement).
  - Fil et preuves : commentaires `action_comments` (jamais supprimés ; retrait avec motif : texte gardé en base, jamais envoyé au navigateur) ; preuve = pièce jointe `entity_type = 'action'`, `attachments.comment_id` quand elle accompagne un commentaire ; preuves d'un commentaire retiré visibles du QHSE seulement (`canReadAttachment`) ; retrait d'une preuve (`canRemoveProof`, avant Vérifiée) : ligne supprimée et journal dans la même transaction (`deleteAttachment(id, { db: tx })`, puis `removeStoredFile` après validation).
  - Notifications stockées (`notifications`, `src/server/notify.ts`, dans la transaction de l'écriture ; entité `action`, ou `event` pour « Suite de votre signalement » au déclarant nominatif qualifié / classé / clôturé, TDB-06, lien « Mes signalements ») : « Action confiée » au responsable à la création et à la réaffectation (cloche seulement, jamais d'e-mail) ; ACT-31 : un commentaire ou une preuve du responsable (hors QHSE) notifie chaque animateur QHSE, une notification par commentaire ou par fichier (`comment_id` : titre réécrit au retrait). Cloche (`src/lib/data/notifications.ts`) : clé `notification:<id>` (état lu dans `notifications.read_at`), lien gardé seulement si `canReadAction`.
  - Rappel du mercredi (ACT-32/33) : élément de la cloche calculé (jamais un `TodoItem`), clé `rappel-actions|<semaine ISO>`, actions ouvertes (retards d'abord) puis Terminées en attente de vérification, Reportées exclues ; e-mail par la tâche planifiée `src/lib/action-reminder-job.ts` (journal `action_reminder_sends`, un envoi par personne et semaine). Tâches planifiées : `src/db/scheduler.ts` (registre `scheduledTasks`, construit et démarré par `open()` si `VIGIE_SCHEDULER`, jamais pendant `next build`, `VIGIE_SCHEDULER=0` dans `vitest.config.mts`) ; transport `src/lib/mail/transport.ts` (`VIGIE_MAIL_TRANSPORT` `aucun` | `fichier`, `VIGIE_MAIL_DIR`, `VIGIE_MAIL_FROM`, `VIGIE_REMINDER_TIME` ; SMTP / Graph : ACT-34).
  - Reprise 0005 : `actions.legacy_origin` (ancienne origine, écrite par la seule migration, lue par `reprise-liens` et comme indice d'une source « à compléter » ; à supprimer après ACT-37). `npm run db:check` étape 5b : forme de la base migrée comparée à l'instantané (`src/db/shape.ts`).
- Toute nouvelle échéance transverse (le rappel du mercredi et les notifications stockées n'en sont pas) passe par `load<Domaine>Signals()` puis `src/lib/data/todo.ts` (tableau de bord, notifications) et `counters.ts` (badges). Les signaux sont calculés sur tout le périmètre (scope `'perimeter'`) et portent `siteId` (null : élément commun à l'entreprise), `ownerIds` (responsables désignés), `dueOn` (date d'échéance réelle, aussi pour un retard daté du jour : tri des retards par ancienneté, et clé d'état lu `todoKey` = base|gravité|dueOn, TDB-07 — jamais `date` ni une durée relative dans la clé) et, pour un écran fermé à certains de ces responsables, `readHref` (vue en lecture, ex. `/audits/contributions`). Visibilité : règle pure `visibleTodo` (`src/lib/todo-visibility.ts`, via `loadVisibleTodo`) — site sélectionné et écran modifiable par le rôle, plus les échéances de la personne sur tout son périmètre ; `openTodo` (`src/server/notifications.ts`) sélectionne le site de l'échéance avant de l'ouvrir.
- Signalement terrain : `/signaler` (bouton « Nouveau signalement » ; `/apercu-mobile` en démonstration seulement). Le QR code de poste porte un jeton HMAC (`src/lib/report-token.ts`, `VIGIE_REPORT_SECRET`, version `map_zones.qr_version` incrémentée par « Régénérer le QR ») ; sans session, `createReport` n'accepte qu'un jeton valide, avec les protections de `src/lib/report-guard.ts` (champ piège, photos contrôlées, puis limite de débit en base : par client normalisé — IPv6 par /64, adresse lue dans `X-Forwarded-For` selon `VIGIE_TRUSTED_PROXIES` —, puis par poste dans la transaction qui crée l'événement ; plafond du poste journalisé et signalé par `loadReportPostSignals`). Signalement anonyme : `reported_via = 'terrain'`, photos renommées (`anonymousPhoto`). URL publique des QR codes : `publicOrigin()` (`src/lib/public-url.ts`), jamais l'en-tête Host.
- Données de santé d'un AT (blessure, jours perdus, déclaration CPAM, nature et siège des lésions, soins, réserves, toute donnée médicale) : animateur QHSE et direction seulement (`canSeeHealth`, `src/lib/domain.ts`). Pièce jointe médicale : `saveUpload(…, { health: true })` (`attachments.health`), refusée par `canReadAttachment` (`/fichiers`) aux autres rôles ; registre des accidents bénins (`/evenements/registre-benin`, un par site) réservé aux mêmes rôles, inscription contrôlée par `benignRegisterBlocker()`. L'intitulé et la description d'un AT ne portent pas la lésion (aide de saisie). Champs listés dans `HEALTH_LABELS` (`src/components/events/shared.ts`) : retirés des chargements des autres rôles (`withoutHealth`, `loadEventDetail`, `loadEventChangeLog` — jamais dans la charge RSC), refusés par les server actions (`HEALTH_DENIED`), affichés « Données restreintes » ; échéance qui en révèle une : `health: true` (filtrée par `loadVisibleTodo`). Les agrégats (TF1/TG, pyramide) restent visibles. Toute nouvelle donnée médicale s'ajoute à `HEALTH_LABELS`.
- Dates : jour de Paris d'un horodatage par `parisDay` (`src/lib/dates.ts`), jamais `toISOString().slice(0, 10)` (QUA-09). Historique d'une fiche : chargé à l'ouverture (`LazyChangeLog` + `loadEntityHistory`, `src/server/history.ts`, mêmes droits que l'écran : `RULES` par entité, `allow` quand l'historique n'est montré qu'à la saisie) plutôt qu'avec toute la liste (QUA-11 : veille, prévention ; paquet 3 : sites, carte, activités, unités et versions du DUERP, fiche salarié et case de la matrice, documents, relevés).
- Revue de direction : visa (clôture, dossier figé) réservé à la direction (`canSignReview`, AUD-15), après les contrôles purs de `reviewCloseBlockers` (`src/lib/review-rules.ts` : participants, synthèse, pilote de chaque décision, AUD-14). Exigence de veille : vaut pour l'entreprise (contrôles rattachés et indicateur R. 4512-6 sur tout le périmètre, VEI-06) ; suivie par des contrôles, son échéance est celle du prochain contrôle (`requirementDue`, `src/lib/queries.ts`, VEI-03).
- Libellés, tons, rôles et navigation : `src/lib/domain.ts`. Styles : `src/app/nocturne.css` (copie du DS, ne pas modifier) et `src/app/vigie.css` ; navigation sur téléphone : `src/components/AppShell.tsx` (barre supérieure, tiroir).
- Interface et identifiants de route en français ; code en anglais.

## Intégrations prévues
