# Vigie (QHSE) — notes projet

Outil QHSE du système EPC2i (avec Keystone, Codex, Cursus). Maquette source : `design/Vigie.dc.html` (+ `design/_ds/nocturne-…/` pour le design system).

## Next.js 16

Cette version de Next.js a des changements incompatibles avec les versions antérieures (API asynchrones `cookies()`, `params`, `searchParams`…). Lire le guide concerné dans `node_modules/next/dist/docs/` avant d'écrire du code.

## Conventions

- Stack : Next.js 16.4 (App Router) + React 19.3 + Drizzle (PostgreSQL en production, PGlite en démonstration et dans l'application Mac), comme Keystone et Codex. Port de dev : 3200.
- Données : `src/db/schema.ts` → `npm run db:generate` produit la migration dans `drizzle/` ; elle est appliquée à l'ouverture de la base (`src/db/index.ts` : PostgreSQL si `DATABASE_URL`, sinon PGlite), puis, en démonstration seulement, `seed.ts` remplit une base vide. Type commun `Db` / `Tx` / `DbOrTx` (`src/db/types.ts`) : n'utiliser que l'API Drizzle commune aux deux moteurs. Tout écran tolère une base sans site ni personne (amorçage : `src/components/Bootstrap.tsx`).
- **Migrations : une migration publiée ne se modifie jamais** (SQL, instantané `drizzle/meta/`, date du journal) — le migrator ne rejoue pas une migration déjà appliquée. Tout changement de schéma passe par une nouvelle migration (`npm run db:generate`), enregistrée dans `drizzle/checksums.json` par `npm run db:check -- --enregistrer` une fois définitive ; `npm run db:check` (CI) vérifie empreintes, journal, `drizzle-kit check`, écart schéma/migrations et application à une base vide. Avant un déploiement : `npm run db:test-migrate -- <sauvegarde>` (migrations appliquées à une copie restaurée).
- Exploitation (`docs/EXPLOITATION.md`) : image Docker (sortie `standalone` avec `VIGIE_STANDALONE=1`, `Dockerfile`, `docker-compose.yml`), route de santé `/api/sante`, sauvegardes (`src/db/backup.ts`, `scripts/vigie-db.ts` : `db:backup`, `db:restore`, sauvegarde automatique avant migration), pièces jointes chiffrées au repos (`src/lib/encryption.ts`, `VIGIE_UPLOAD_KEY` ; lire et écrire les fichiers par `src/lib/uploads.ts` seulement).
- Configuration : variables d'environnement lues et validées (zod) uniquement dans `src/lib/env.ts` — sans `server-only`, pour `src/proxy.ts`, `src/instrumentation.ts`, les scripts et les tests ; le code applicatif passe par `config()` / `isDemo()` de `src/lib/config.ts`. Aucun autre module ne lit `process.env`. Une variable invalide arrête le serveur au démarrage (`ConfigError`, une ligne par variable). Toute nouvelle variable : `env.ts` (+ `src/lib/env.test.ts`), `.env.example` et le tableau du § 4 de `docs/EXPLOITATION.md`.
- Mode démonstration (`VIGIE_DEMO=1`, `npm run dev`, `npm run start:demo`, application Mac par `VIGIE_DESKTOP=1`) : sélecteur de rôle (`setRole`, cookie `vigie_role`), `VIGIE_TODAY`, jeu de démonstration, `/apercu-mobile` ; tout le reste du comportement est celui de la production. Toute fonctionnalité de démonstration se conditionne par `isDemo()` ; hors démonstration, jamais de rôle ni de personne par défaut. Les identifiants du jeu de démonstration (`clefevre`…) ne figurent que dans `src/lib/demo.ts` et les seeds ; destinataires des alertes : `loadQhseLeads()` (`src/lib/data/leads.ts`, responsable QHSE du site, direction et animateurs par `people.last_role`). Date du jour : `today()` de `src/lib/today.ts` (serveur).
- Les indicateurs (TF1/TG, retards, échéances, statuts de contrôles et d'habilitations) sont **calculés** dans `src/lib/queries.ts` à partir des données et de la date du jour — ne pas les stocker.
- Chargements par écran dans `src/lib/data/<domaine>.ts`, server actions dans `src/server/<domaine>.ts` (validation `formReader`, droits `requireManager` / `requireApprover`, site `requireInSite`, `revalidatePath('/', 'layout')`). Les données portant un `siteId` sont filtrées avec `currentSiteId()` / `inSite`, dans le périmètre de la personne (ci-dessous).
- Session (`src/lib/session.ts`) : `getSession()` → `{ role, user, site, siteOptions, allowedSiteIds, bootstrap, demo }`, redirige sans identité valide (connexion, « Configuration incomplète », « Accès non autorisé ») ; `getOptionalSession()` pour le formulaire public et les routes qui répondent 401/404 ; `currentPersonId()` sans accès à la base (appelable dans une transaction). Identité fournie par `src/lib/auth/` (`getAuthState()` : cookie de démonstration ou session Entra). Pages : `guard(screen)` ; server actions : `requireManager()` / `requireApprover()` (`src/lib/guard.ts`).
- Sites autorisés : `allowedSiteIds` (null = tous les sites : direction, animateur QHSE, démonstration ; sinon site de rattachement + sites accordés par groupe Entra) ; `inPerimeter(allowed, siteId)` en lecture, `activeSiteIds()` pour les listes de choix. Toute écriture sur une donnée portant un `siteId` appelle `requireInSite(siteId)` après le chargement de l'enregistrement, avec `{ create: true }` pour une création ou un changement de site (site actif du périmètre ; « Tous les sites » réservé au périmètre complet). `setSite` et `/fichiers/[id]` refusent un site hors périmètre.
- Traçabilité : jamais de suppression physique d'un enregistrement métier tracé — archivage (`archivedAt` / `archivedById` / `archiveReason`) ou annulation (`cancelledAt` / `cancelledById` / `cancelReason`), avec un motif obligatoire (`formReader(fd).reason()`, `ReasonButton` / `ReasonForm` de `src/components/ReasonDialog.tsx`) ; chaque création, modification, annulation ou archivage est journalisé par `logChange()` (`src/server/changelog.ts`, `diffFields()`), dans la transaction de l'écriture.
- Tests (`npm test`, Vitest) : règles pures dans un `*.test.ts` à côté du module ; server actions et chargements dans `test/integration/`, sur une base de démonstration neuve par fichier (`freshDemoDatabase()`, `actAs(rôle, site)`, `changeLog()` de `test/helpers.ts` ; `next/headers`, `next/cache` et `next/navigation` simulés par `test/next-mocks.ts`), en PGlite en mémoire, ou sur PostgreSQL avec `TEST_DATABASE_URL` (base d'administration : une base créée puis supprimée par fichier, `test/setup-postgres.ts`). Toute nouvelle server action y teste droits, site, motif et journal. Cloisonnement du Salarié dans la charge des pages : `test/e2e/` contre le serveur construit (`VIGIE_E2E_URL`). CI : `.github/workflows/ci.yml` (Node de `.nvmrc`).
- Formulaires : `ActionForm` + `Field`/`Input`/`Select` (`src/components/form.tsx`) dans un `Dialog`/`DialogButton` ; création d'action depuis n'importe quel écran avec `NewActionButton` (champ `link` pour rattacher l'action à sa source).
- Toute nouvelle échéance transverse passe par `load<Domaine>Signals()` puis `src/lib/data/todo.ts` (tableau de bord, notifications) et `counters.ts` (badges).
- Signalement terrain : `/signaler` (bouton « Nouveau signalement » ; `/apercu-mobile` en démonstration seulement). Le QR code de poste porte un jeton HMAC (`src/lib/report-token.ts`, `VIGIE_REPORT_SECRET`, version `map_zones.qr_version` incrémentée par « Régénérer le QR ») ; sans session, `createReport` n'accepte qu'un jeton valide, avec les protections de `src/lib/report-guard.ts` (champ piège, photos contrôlées, puis limite de débit en base : par client normalisé — IPv6 par /64 —, puis par poste dans la transaction qui crée l'événement ; plafond du poste journalisé et signalé par `loadReportPostSignals`). URL publique des QR codes : `publicOrigin()` (`src/lib/public-url.ts`), jamais l'en-tête Host.
- Données de santé d'un AT (blessure, jours perdus, déclaration CPAM, toute donnée médicale) : animateur QHSE et direction seulement (`canSeeHealth`, `src/lib/domain.ts`). Champs listés dans `HEALTH_LABELS` (`src/components/events/shared.ts`) : retirés des chargements des autres rôles (`withoutHealth`, `loadEventDetail`, `loadEventChangeLog` — jamais dans la charge RSC), refusés par les server actions (`HEALTH_DENIED`), affichés « Données restreintes » ; échéance qui en révèle une : `health: true` (filtrée par `loadVisibleTodo`). Les agrégats (TF1/TG, pyramide) restent visibles. Toute nouvelle donnée médicale s'ajoute à `HEALTH_LABELS`.
- Libellés, tons, rôles et navigation : `src/lib/domain.ts`. Styles : `src/app/nocturne.css` (copie du DS, ne pas modifier) et `src/app/vigie.css`.
- Interface et identifiants de route en français ; code en anglais.

## Intégrations prévues

- Habilitations et formations : l'écran doit aussi communiquer avec l'outil **Cursus**, propriétaire des données personnelles des employés (source de vérité RH). Lucca reste la source d'import provisoire du personnel ; Cursus doit apparaître comme connecteur/source dans les futures itérations de cet écran.
- Keystone : projets liés aux événements, affectations du planning (alerte habilitation), projets concernés par la veille.
- Authentification Microsoft Entra ID (branchée ; inscription dans le tenant réel à faire, `docs/EXPLOITATION.md` § 3) : hors démonstration, `getSession()` (`src/lib/session.ts`) lit l'identité du cookie de session chiffré (`src/lib/auth/entra.ts`, établi par `/auth/retour` ; 8 h glissantes, 12 h au plus, `VIGIE_SESSION_SECRET`) ; fiche rapprochée par `people.entra_object_id`, sinon par e-mail, sinon créée (`src/lib/auth/person.ts`) ; rôle = rôle applicatif Entra le plus élevé, périmètre = site de rattachement + `VIGIE_SITE_GROUPS` (`session.allowedSiteIds`, contrôlé par `setSite`, `requireInSite`, `/fichiers`). `src/proxy.ts` : hôtes admis, connexion requise (routes publiques : `/auth/*`, `/api/sante`, `/signaler?jeton=`), CSP à nonce, HSTS ; en-têtes fixes dans `next.config.ts`. Tests sans tenant : `scripts/oidc-mock.mjs` + `scripts/e2e-auth.sh`.
