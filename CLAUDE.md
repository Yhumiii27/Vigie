# Vigie (QHSE) — notes projet

Outil QHSE du système EPC2i, avec Keystone (projets), Codex (documents), Cursus (RH), Matrix (serveur PostgreSQL commun, référentiels et journal unifié), Arche (CAPEX des filiales) et Crucible (moyens d'essais R&D). Demandes entre applications : `REQUESTS.md` à la racine de chaque dépôt (boîte aux lettres inter-applications ; celle de Vigie reçoit les demandes des autres outils, une demande à un autre outil va dans le sien, validée par Guillaume). Maquette source : `design/Vigie.dc.html` (+ `design/_ds/nocturne-…/` pour le design system).

## Next.js 16

Cette version de Next.js a des changements incompatibles avec les versions antérieures (API asynchrones `cookies()`, `params`, `searchParams`…). Lire le guide concerné dans `node_modules/next/dist/docs/` avant d'écrire du code.

## Conventions

- Stack : Next.js 16.4 (App Router) + React 19.3 + Drizzle (PostgreSQL en production, PGlite en démonstration et dans l'application Mac), comme Keystone et Codex. Port de dev : 3200.
- Données : `src/db/schema.ts` → `npm run db:generate` produit la migration dans `drizzle/` ; elle est appliquée à l'ouverture de la base (`src/db/index.ts` : PostgreSQL si `DATABASE_URL`, sinon PGlite), puis, en démonstration seulement, `seed.ts` remplit une base vide (orchestration ; jeu par domaine dans `src/db/seeds/*.ts`, QUA-26 ; dates jamais en dur : `rel(n)` = écart en jours à `DEMO_REFERENCE_DAY` 2026-10-09 de `src/db/seeds/dates.ts`, QUA-20, `dates.test.ts`). Type commun `Db` / `Tx` / `DbOrTx` (`src/db/types.ts`) : n'utiliser que l'API Drizzle commune aux deux moteurs. Tout écran tolère une base sans site ni personne (amorçage : `src/components/Bootstrap.tsx`).
- Serveur PostgreSQL commun EPC2I (décision M-01 du 15/10/2026 ; P-02, migrations publiées réécrites à l'application, et P-03, pas de reprise de données, du 18/10/2026) : tables, vues `pub_` et journal (`vigie.__drizzle_migrations`) dans le schéma `vigie` (`SERVER_SCHEMA`, `DB_LAYOUT` de `src/db/migrations.ts`), `search_path=vigie` sur le pool ; `schema.ts` garde `pgTable` et les migrations publiées restent intactes : `migrateServer()` y remplace `"public".` par `"vigie".` au moment de les appliquer, sous `pg_advisory_lock(hashtext('vigie.migrations'))`, sans `CREATE SCHEMA` ; chaque `db.transaction()` y prend `pg_advisory_xact_lock(hashtext('vigie.ecritures'))` (écritures sérialisées comme dans PGlite). PGlite reste dans `public` (journal `drizzle.__drizzle_migrations`). SQL écrit à la main (vues `pub_` : `drizzle/0009_partage.sql`) : noms non qualifiés, ou `"public".` ; jamais une donnée de santé dans une vue `pub_`, ni un événement AT ou de `HEALTH_EVENT_TYPES` dans `pub_journal` ni dans `pub_hse_projet` (`test/integration/server-layout.test.ts`, `share-health-views.test.ts`) ; `npm run db:check` étape 6 contrôle la disposition du serveur. Nouvelle donnée de santé (colonne de `HEALTH_LABELS`) : la faire inscrire comme colonne sensible côté Matrix (`init/03-droits.sql`, `partage/90-droits.sql`) avant de déployer la migration ; vue `pub_` redéfinie par une migration : copie Matrix `partage/50-vigie.sql` à mettre à jour — demandes par le `REQUESTS.md` de Matrix, validées par Guillaume (`docs/EXPLOITATION.md` § 2). Vue `pub_controles` (`drizzle/0014_controls_share.sql`, demande de Crucible) : contrat Crucible v1, lecteur `crucible_app` (droit accordé par Matrix), colonnes ajoutées en fin seulement, tous les contrôles (en vigueur et archivés) avec le code commun d'équipement `controls.equipment_code` (saisi dans la fiche du contrôle, `equipmentCodeError` de `src/lib/watch-rules.ts`, non unique), `maj_le` calculé d'après le journal et les enregistrements ; ni personne ni donnée de santé (`test/integration/controls-share.test.ts`).
- **Migrations : une migration publiée ne se modifie jamais** (SQL, instantané `drizzle/meta/`, date du journal) — le migrator ne rejoue pas une migration déjà appliquée. Tout changement de schéma passe par une nouvelle migration (`npm run db:generate`), enregistrée dans `drizzle/checksums.json` par `npm run db:check -- --enregistrer` une fois définitive ; `npm run db:check` (CI) vérifie empreintes, journal, `drizzle-kit check`, écart schéma/migrations et application à une base vide. Avant un déploiement : `npm run db:test-migrate -- <sauvegarde>` (migrations appliquées à une copie restaurée).
- Exploitation (`docs/EXPLOITATION.md`) : image Docker (sortie `standalone` avec `VIGIE_STANDALONE=1`, `Dockerfile`, `docker-compose.yml`), route de santé `/api/sante`, sauvegardes (`src/db/backup.ts`, `scripts/vigie-db.ts` : `db:backup`, `db:restore`, sauvegarde automatique avant migration ; restauration : empreintes des pièces jointes contrôlées, archive en clair refusée avec une clé sauf `--accepter-clair`, PGlite rechargé sur place : `VIGIE_UPLOAD_DIR` et `VIGIE_BACKUP_DIR` jamais dans `VIGIE_DATA_DIR`), pièces jointes chiffrées au repos (`src/lib/encryption.ts`, `VIGIE_UPLOAD_KEY` ; lire et écrire les fichiers par `src/lib/uploads.ts` seulement). Une base migrée par une version plus récente est refusée à l'ouverture (`NewerDatabaseError`, `src/db/migrations.ts`) ; purge horaire des empreintes d'IP et des fichiers orphelins de plus de 24 h (`src/db/maintenance.ts`). Journal du serveur (PRD-10) : `log.info|warn|error(événement, message, champs)` de `src/lib/log.ts` (JSON sur la sortie standard, `VIGIE_LOG_LEVEL`, `VIGIE_LOG_FORMAT`), jamais `console.*` côté serveur ; jamais de secret, de donnée de santé, de saisie libre, d'adresse IP ni de paramètre d'URL dans un champ (masqués d'après leur nom) ; erreurs serveur par `onRequestError` (`src/instrumentation.ts`). Application Mac cliente du serveur central : `VigieServerURL` (`desktop-app/README.md`).
- Configuration : variables d'environnement lues et validées (zod) uniquement dans `src/lib/env.ts` — sans `server-only`, pour `src/proxy.ts`, `src/instrumentation.ts`, les scripts et les tests ; le code applicatif passe par `config()` / `isDemo()` de `src/lib/config.ts`. Aucun autre module ne lit `process.env`. Une variable invalide arrête le serveur au démarrage (`ConfigError`, une ligne par variable). Toute nouvelle variable : `env.ts` (+ `src/lib/env.test.ts`), `.env.example` et le tableau du § 4 de `docs/EXPLOITATION.md`.
- Mode démonstration (`VIGIE_DEMO=1`, `npm run dev`, `npm run start:demo`, application Mac par `VIGIE_DESKTOP=1`) : sélecteur de rôle (`setRole`, cookie `vigie_role`), `VIGIE_TODAY`, jeu de démonstration, `/apercu-mobile` ; tout le reste du comportement est celui de la production. Toute fonctionnalité de démonstration se conditionne par `isDemo()` ; hors démonstration, jamais de rôle ni de personne par défaut. Les identifiants du jeu de démonstration (`clefevre`…) ne figurent que dans `src/lib/demo.ts` et les seeds ; destinataires des alertes : `loadQhseLeads()` (`src/lib/data/leads.ts`, responsable QHSE du site, direction et animateurs par `people.last_role`). Date du jour : `today()` de `src/lib/today.ts` (serveur).
- Les indicateurs (TF1/TG, retards, échéances, statuts de contrôles et d'habilitations) sont **calculés** dans `src/lib/queries.ts` à partir des données et de la date du jour — ne pas les stocker. TF1/TG : `safetyRates()` sur les 12 derniers mois complets (`lastFullMonths()`), mois sans heures signalés ; TF1/TG, jours sans accident et pyramide ne comptent que les accidents de l'effectif, hors accident de trajet (`workforceAccident()`, `events.commute`, EVT-09) ; objectifs QHSE mesurables (AUD-13) : indicateur calculé et cible (`qhse_objectives`), valeur et état calculés à l'affichage (`src/lib/objectives.ts`, `src/lib/objective-values.ts`, `loadObjectives`), cible TF1 du tableau de bord et du dossier de revue = objectif « tf1 » de l'année (`tf1Target`, plus de constante) ; qui déclare un AT selon la victime (salarié : CPAM ; intérimaire : l'ETT, informée sous 24 h ; personne extérieure : son employeur) : `declarationDuty()` (`src/components/events/shared.ts`) ; délais d'un AT (48 h CPAM hors dimanches et fériés, option Alsace-Moselle du site, ETT, réserves) : `src/components/events/deadlines.ts` ; heure locale de Paris : `src/lib/dates.ts`.
- Chargements par écran dans `src/lib/data/<domaine>.ts`, server actions dans `src/server/<domaine>.ts` (validation `formReader`, droits `requireManager` / `requireApprover`, site `requireInSite`, `revalidatePath('/', 'layout')`). Les données portant un `siteId` sont filtrées avec `currentSiteId()` / `inSite`, dans le périmètre de la personne (ci-dessous) ; `siteFilter('perimeter')` (et `scope` des chargements de `queries.ts`) pour tout le périmètre. Écran en consultation seule (`isReadOnly(role, écran)`, ex. DUERP pour le Salarié, Audits pour l'encadrement) : écritures refusées par `canEdit(role, écran)` côté serveur, charge de la page sans listes de formulaire ni données d'autrui.

Identité fournie par `src/lib/auth/` (`getAuthState()` : cookie de démonstration ou session Entra). Pages : `guard(screen)`, doublé avant le rendu par `src/proxy.ts` (`ROLE_ROUTES` et `HEALTH_PAGES` de `src/lib/auth/route-access.ts`, à tenir à jour avec toute nouvelle page : `route-access.test.ts` les compare aux appels `guard()`) ; server actions : `requireManager()` / `requireApprover()` (`src/lib/guard.ts`).
- Sites autorisés : `allowedSiteIds` (null = tous les sites : direction, animateur QHSE, démonstration ; sinon site de rattachement + sites accordés par groupe Entra) ; `inPerimeter(allowed, siteId)` en lecture, `activeSiteIds()` pour les listes de choix ; listes de sites des formulaires : `loadFormOptions()` (`writableSites()` : exactement les sites qu'accepte `requireInSite(…, { create: true })`, `allSites` pour « Tous les sites »).
